# python-ebics-client v0.1.0: implementation plan

Goal: an MIT, pure-Python EBICS 3.0 (H005, BTF) client built on `cryptography` and `lxml`, so
Python projects (ERPNextSwiss, ALYF banking, Noviat account_ebics, pretix-ebics) can talk EBICS
3.0 without the proprietary `fintech` package or a Node.js sidecar.

Distribution name `python-ebics-client` on PyPI, import name `ebics_client`. Python 3.9+.
Runtime dependencies: `cryptography>=41`, `lxml>=4.9`. HTTP through the standard library
(`urllib.request`), pluggable.

Repository: `/home/dylanmerigaud/Code/python-ebics-client`, GitHub
`DylanMerigaud/python-ebics-client`. Virtualenv: `.venv` (already has cryptography, lxml, pytest,
ruff, mypy, build, lxml-stubs). Run tests: `.venv/bin/python -m pytest -q`.

## 1. Specs and references

- EBICS 3.0.2 specification and the H005 XML schemas (ebics.org, "Specification", EBICS 3.0).
  The official H005 XSDs are vendored under `tests/xsd/H005/` (copied from
  `/home/dylanmerigaud/.cache/ebics-ref/epics/spec/xsd/H005/`, which railslove/epics ships under
  MIT; their origin is ebics.org). Every H005 request the library builds and every H005 response the
  test bank builds is validated against them in the tests; HEV (H000) is tested but not
  schema-validated, no H000 schema is vendored.
- Reference implementations, read for behaviour only (no code copied):
  railslove/epics (Ruby, MIT), local copy at `/home/dylanmerigaud/.cache/ebics-ref/epics/lib/`

  `services/crypt_service.rb`, `letter_renderer.rb`); node-ebics-client (MIT) on GitHub.
- Swiss Payment Standards, EBICS implementation guidelines (BTF mapping for CH order types:
  camt.052/053/054 with Scope CH), DK (German Banking Industry Committee) Annex 3 BTF mapping.

## 2. Protocol facts the code must hold (H005)

- Namespaces: EBICS `urn:org:ebics:H005`, signature `http://www.ebics.org/S002`, XML-DSig
  `http://www.w3.org/2000/09/xmldsig#`, HEV `http://www.ebics.org/H000`. Root attributes
  `Version="H005" Revision="1"`.
- Keys: RSA 2048 bit minimum (we generate 2048 by default, accept 2048 to 4096).
  A006 = electronic signature, RSASSA-PSS, SHA-256, MGF1 SHA-256, salt length 32, applied to
  the SHA-256 hash of the normalized order data (CR, LF and Ctrl-Z removed), so the data is
  hashed twice: once for the EBICS hash value, once inside PSS. railslove/epics and
  node-ebics-client sign the same way. The normalized document is also what is sent.
  X002 = authentication, RSASSA-PKCS1-v1_5 SHA-256 over the canonical SignedInfo.
  E002 = encryption: a random 16 byte AES-128 transaction key, AES-128-CBC with a zero IV and the
  EBICS padding (pad to the next full block, ALWAYS at least one byte, zero bytes, last byte =
  number of pad bytes); the transaction key is encrypted RSAES-PKCS1-v1_5 with the recipient's
  public key. Order data is zlib-compressed before encryption, decompressed after decryption.
- Certificates: H005 transmits keys as X.509 certificates (`ds:X509Data` with
  `ds:X509IssuerSerial` and `ds:X509Certificate`). Self-signed certificates are allowed in
  Germany and Switzerland (generated by the library: basicConstraints CA:FALSE, keyUsage,
  validity until 9999-12-31 by default, SHA-256). CA-issued certificates (France) are loaded by
  the user and sent with H3K.
- Key digests in H005 (BankPubKeyDigests, EncryptionPubKeyDigest, INI letter hashes): SHA-256 of
  the DER certificate. Algorithm URI `http://www.w3.org/2001/04/xmlenc#sha256`.
- Authentication signature (X002): `AuthSignature` element after `header`; SignedInfo with
  CanonicalizationMethod `http://www.w3.org/TR/2001/REC-xml-c14n-20010315`, SignatureMethod
  `http://www.w3.org/2001/04/xmldsig-more#rsa-sha256`, one Reference with
  `URI="#xpointer(//*[@authenticate='true'])"`, Transform c14n, DigestMethod
  `http://www.w3.org/2001/04/xmlenc#sha256`. DigestValue = SHA-256 of the concatenated inclusive
  c14n of every element carrying `authenticate="true"` in document order. SignatureValue = X002
  signature of the c14n of SignedInfo. The same algorithm verifies the bank's responses.
- Transactions: Initialisation, Transfer (one request per further segment, segment size 1 MB of
  the base64 order data), Receipt (downloads only, ReceiptCode 0 to acknowledge, 1 to refuse).
  Return codes: technical in header/mutable/ReturnCode, business in body/ReturnCode, both
  `000000` on success; `090005` no download data available.
- Order types used: HEV (version check), INI (A006 certificate, unsecured request), HIA (X002 and
  E002 certificates, unsecured), H3K (all three CA certificates, unsigned request signed with
  A006), HPB (bank's X002 and E002 certificates, no-pub-key-digests request, encrypted response),
  BTD (download with a BTF Service, optional DateRange), BTU (upload with a BTF Service, A006
  signature attached, file name optional).
- BTF Service element order (RestrictedServiceType in ebics_orders_H005.xsd): ServiceName,
  Scope, ServiceOption, Container, MsgName (with `version` and optional `variant`, `format`
  attributes). Check the XSD.

## 3. Public API (what the README shows)

```python
from ebics_client import Bank, User, Keyring, EbicsClient, Service, letter

bank = Bank(host_id="EBIXHOST", url="https://ebics.example-bank.ch/ebicsweb")
user = User(partner_id="PARTNER1", user_id="USER1")
keyring = Keyring.generate(user, subject_country="CH")          # A006, X002, E002 + self-signed certs
keyring.save("keys.json", passphrase="secret")                  # encrypted at rest
keyring = Keyring.load("keys.json", passphrase="secret")

client = EbicsClient(bank, user, keyring)
client.hev()                       # -> list[ProtocolVersion] the bank supports
client.ini(); client.hia()         # send our certificates
print(letter.ini_letter(bank, user, keyring))   # text letter with the SHA-256 hashes
client.hpb()                       # fetch and store the bank's X002 and E002 certificates
keyring.bank_keys_verified = True  # only after comparing with the bank's letter (hashes shown)

for doc in client.download(Service.CAMT_053_CH, start=date(2026, 10, 1), end=date(2026, 10, 31)):
    ...                            # bytes of each file (ZIP containers unpacked)

client = EbicsClient(bank, user, keyring, allow_uploads=True)
client.upload(Service.PAIN_001_CH, pain001_bytes)   # returns the order id
```

- `EbicsClient(..., transport=callable)`: `transport(url: str, body: bytes) -> bytes`; default
  posts with urllib (content type `text/xml; charset=UTF-8`, timeout configurable).
- Uploads refuse with `UploadsDisabled` unless `allow_uploads=True` (payment liability: the
  library starts read-only by default).
- Downloads refuse when the bank keys were never verified unless `require_verified_bank_keys`
  is False (default True, the INI letter step must be done).
- `Service` is a frozen dataclass (`name`, `scope`, `option`, `container`, `msg_name`,
  `msg_version`, `variant`, `format`), with presets: `CAMT_052_CH`, `CAMT_053_CH`,
  `CAMT_054_CH`, `PAIN_001_CH`, `PAIN_008_CH`, `CAMT_052_DE`, `CAMT_053_DE`, `CAMT_054_DE`,
  `PAIN_001_DE` (SCT), `PAIN_008_DE` (SDD core). Each preset cites its source in its docstring.
- Errors: `EbicsError(code, text)` base, `EbicsTechnicalError`, `EbicsBusinessError`,
  `NoDownloadData` (090005), `UploadsDisabled`, `BankKeysNotVerified`, `SignatureInvalid`.
- `ebics_client.testing.FakeBank`: an in-process EBICS H005 bank (holds its own X002/E002 keys,
  answers HEV, INI, HIA, H3K, HPB, BTD from files the test registered, BTU storing the uploaded
  file after verifying the A006 signature and the X002 authentication). Usable as the client's
  transport: `EbicsClient(..., transport=fake_bank)`. It is how users test their integration
  offline and how the README quickstart runs offline.
- Fully typed, `py.typed` shipped.

## 4. Tasks (test first, one at a time)

T1 (opus) crypto, certificates, keyring, letter
- `ebics_client/crypto.py`: generate RSA keys, A006 sign/verify, X002 sign/verify, E002
  encrypt/decrypt (transaction key + AES with EBICS padding), zlib helpers, certificate digest,
  self-signed certificate generation.
- `ebics_client/keyring.py`: `User`, `Keyring` (user keys + certs, bank certs, verified flag),
  save/load as JSON with keys as PKCS#8 PEM encrypted by the passphrase (BestAvailableEncryption),
  file mode 600; loading a CA certificate for H3K.
- `ebics_client/letter.py`: INI/HIA letter (text) with user, partner, host, date, certificate
  issuer and serial, SHA-256 hashes in hex grouped by 2 bytes, signature lines.
- Tests: padding round-trips (edge cases: len % 16 == 0 still adds a full block), PSS verify by
  `cryptography` directly, a wrong key fails, keyring round-trip, wrong passphrase refused,
  digest equals sha256(DER), letter contains the three hashes.

T2 (opus) XML: auth signature and request builders, response parsing
- `ebics_client/xmlsig.py`: sign and verify the X002 AuthSignature per section 2.
- `ebics_client/requests.py`: builders for HEV, INI, HIA, H3K, HPB, BTD init/transfer/receipt,
  BTU init/transfer; Nonce 16 random bytes hex upper, Timestamp UTC ISO with Z.
- `ebics_client/responses.py`: parse return codes, transaction id, segments, decrypt order data.
- Tests: every built request validates against `tests/xsd/H005/ebics_H005.xsd` (the keymgmt
  ones too); auth signature verifies; tampering with an authenticated element breaks it.

T3 (opus) FakeBank and EbicsClient
- `ebics_client/testing.py` FakeBank (written from the spec independently of the client
  helpers where it verifies: its own c14n digest and signature checks).
- `ebics_client/client.py` EbicsClient with hev, ini, hia, h3k, hpb, download, upload, segment
  handling, receipt, ZIP container unpacking, the two safety flags.
- Tests: full flows against FakeBank (INI, HIA, HPB, download with 1 and 3 segments, 090005,
  upload with signature verified by the bank, uploads disabled by default, unverified bank keys
  refused, bank response with a bad signature refused); FakeBank responses validate against the
  XSD.

T4 (sonnet) packaging and docs
- `pyproject.toml` (hatchling, MIT, classifiers, urls, `[project.optional-dependencies] test`),
  `ruff.toml`, `.github/workflows/ci.yml` (Python 3.9 to 3.13, ruff, mypy, pytest),
  `.github/ISSUE_TEMPLATE/`, `CHANGELOG.md`, `CONTRIBUTING.md`, `LICENSE` (MIT, Dylan Merigaud),
  `docs/` (guide: onboarding a bank step by step, order types table, security notes),
  `examples/` (each runs offline against FakeBank when `OSS_LIB_OFFLINE=1` or always),
  README (what and for whom first, install, quickstart running offline against FakeBank, a usage
  block per feature, the comparison table with fintech, schulluk ebicsclient, ebicsPy,
  node-ebics-client, epics, and an adoption section for ERPNextSwiss, ALYF banking, Noviat
  account_ebics, pretix-ebics showing how their current fintech calls map onto this API).
